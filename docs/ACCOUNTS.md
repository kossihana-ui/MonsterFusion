# アカウント作成システム：設計

2026-11-14。「セーブよりアカウント作成システムがいい」への回答です。

## 1. 先に、ひとつだけ反対意見

**アカウント作成を遊ぶ前に置くと、宣伝なしで広がるかの実験そのものが壊れます。**

知らない人がリンクを踏んで最初に見るのが登録フォームだと、ほとんどの人はそこで閉じます。「面白いかどうか」を判断する前に手続きを求められるためです。宣伝なしで広がるかを試すなら、**最初の5分で遊ばせて、残したくなってから登録させる**のが唯一の形です。

そのうえで、アカウント自体には明確な価値があります。**反対しているのは「順番」だけです。**

| アカウントで本当に解決すること | |
|---|---|
| 別の端末で続きを遊ぶ | ローカル保存では不可能 |
| ブラウザのデータを消しても残る | 同上 |
| 世界ランキングに名前を出す | 同じ人だと言える仕組みが要る |
| 名前を他人に取られない | 同上 |

## 2. ローカル保存は「代わり」ではなく「土台」です

**本日ローカル保存を実装しました。** これはアカウントの代替ではなく、アカウントがあっても必要なものです。

- 保存のたびにサーバー往復すると、戦闘1ターンごとに通信が要ります
- 電波の悪い場所やオフラインで遊べなくなります
- サーバーが落ちた日に全員が遊べなくなります

実際の作りは「**ローカルが正、サーバーは同期先**」です。そして**いま保存しているJSONが、そのままアカウントに入れる中身です。**

```
localStorage: monsterfusion.save.v1
  { version, savedAt, rng, season, core: { monsters, loadouts, inventory, items, arena, session } }
```

つまり**アカウント化は「この塊をサーバーにも置く」だけ**で、作り直しは発生しません。

## 3. 認証方式：匿名アカウント＋あとから連携をおすすめします

| 方式 | 登録の手間 | こちらが預かるもの | 評価 |
|---|---|---|---|
| **匿名（端末ID自動発行）** | **ゼロ** | 何もなし | **おすすめ。最初はこれだけでよい** |
| OAuth（Google / Discord など） | 1タップ | 預からない（相手側が認証） | 連携用に後から追加 |
| メール（マジックリンク） | 入力＋受信 | **メールアドレス＝個人情報** | 必要になってから |
| ID＋パスワード | 多い | **パスワード＝漏洩責任** | 避けたい |

**最初のプレイで黙って匿名アカウントを作ります。** 入力は一切なし。プレイヤーは登録したことにも気づきません。そのうえで、

- 良い記録が出たとき
- 別の端末で遊びたくなったとき

に「この記録を残しますか？」としてGoogle/Discord連携を案内します。**これなら登録フォームが入口に立ちません。**

**個人情報を預からないのは大きな利点です。** 現在このゲームが集めている個人情報はゼロで、匿名IDのままならその状態を維持できます。メールアドレスを預かった瞬間に個人情報保護法の管理義務が発生し、問い合わせ窓口・削除対応・漏洩時の報告義務がついてきます。**遊ばれるかどうか分からない段階で背負うものではありません。**

## 4. サーバーに必要なもの

### データ

```
players   id(uuid) / display_name / created_at / linked_provider(nullable)
saves     player_id / blob(json) / updated_at        ← 上のJSONそのまま
runs      player_id / season / wins / monster / look / ending / at / verified
```

`saves` は1人1行で上書き。`runs` は追記のみでランキングの元になります。

### API

```
POST /session            匿名IDを発行（初回のみ）
GET  /save               自分のセーブを取得
PUT  /save               セーブを保存（updated_at で後勝ち）
POST /runs               連勝記録を提出
GET  /ranking?season=…   上位を取得
POST /link               OAuthで既存の匿名IDに紐づけ
```

### 作り方

**自前でサーバーを書く必要はありません。** Supabase か Cloudflare（Workers + D1）なら、匿名認証・DB・ホスティングが無料枠に収まります。遊ばれる人数が読めない段階では、サーバー運用を背負わないほうが得です。

### 2つの端末で遊んだとき

後勝ち（`updated_at` が新しいほうを採用）で十分です。ただし**古い端末のセーブで上書きされると進行が消えます**。「サーバーのほうが新しいようです。どちらを使いますか？」と聞く画面を1つ用意してください。ここを黙ってやると苦情になります。

## 5. 不正について、正直なところ

**セーブはクライアントが書くので、中身は編集できます。** localStorageでもサーバーでも同じです。これは1人用の進行なので、許容してよい部分です。

**ランキングは別です。** 提出された連勝数を信じてはいけません。coreが完全に決定的なので、**「シード＋入場個体＋行動列」を送らせてサーバーで再実行すれば検証できます**（[WORLD_RANKING.md](../../MonsterFusion-Core/docs/WORLD_RANKING.md) の3章）。`runs.verified` はそのための列です。

検証なしで出すなら、**ランキングは「自己申告の順位表」だと明記**しておくほうが誠実です。

## 6. 順番の提案

| | やること | 規模 | いつ |
|---|---|---|---|
| ✅ | ローカル保存 | 済 | 本日完了 |
| 1 | OGP画像とdescription | 小 | **公開前** |
| 2 | 初見が10分で終わらないようにする | 小〜中 | **公開前** |
| 3 | 公開して、遊ばれ方を見る | — | ここで一度止める |
| 4 | 匿名アカウント＋セーブ同期 | 中 | 遊ばれていたら |
| 5 | 連勝の提出とランキング | 中 | 同上 |
| 6 | OAuth連携 | 小 | 「端末を変えたい」が出たら |

**3で一度止めることをおすすめします。** アカウントは、遊ぶ人がいて初めて意味を持ちます。誰も遊ばなかった場合、アカウント基盤は丸ごと無駄になり、運用だけが残ります。逆に遊ばれていれば、4と5を作る根拠も、どう作るべきかの情報も手に入ります。

**いま作るなら止めません。** その場合は匿名アカウント（3章）から始めてください。入口にフォームを置かない形なら、公開実験の邪魔になりません。
