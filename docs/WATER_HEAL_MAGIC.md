## 2. 公開API

```ts
getMoveHealing('hydro-ram', monster)          // その個体の回復量
getMoveHealing('hydro-ram', monster, config)  // 設定を差し替える場合
```

**HP上限で切り詰める前の値**を返します。図鑑・技説明はこれを使ってください。

回復しない技に渡しても安全で、0が返ります（`attack` も0）。使う前に回復技かどうかを調べる必要はありません。

```ts
scaleHeal(nominal, magic, config?)   // 低レベル版。Monsterではなく魔力の数値を取ります
```

戦闘中は `Combatant`、UIは `Monster` と、持っているものが違うので、計算の本体は魔力の数値だけを取るようにしています。どちらから聞いても同じ答えになります。

**`getMoveBehavior(skillId).heal` は技が名乗っている数値（30）です。** 個体の回復量ではありません。現在UIが「HPを30回復」に使っているのはこちらなので、`getMoveHealing` に差し替えてください。

## 3. 数値

```ts
DEFAULT_BATTLE_CONFIG.healScaling
// { referenceMagic: 70, perMagic: 0.1, minRatio: 0.8, maxRatio: 1.2 }
```

魔力70で技どおりの30。魔力10につき1増減し、0.8〜1.2倍（24〜36）で止まります。四捨五入した整数です。**いただいた調整案そのままです。**

**上下限はHPの実数ではなく倍率で持っています。** 24と36を直接書くと、2つ目の回復技（たとえば回復50）を足したときにこの数値の意味が変わってしまうためです。倍率なら技ごとに正しく効きます。変えたい場合は `healScaling` の4つの値だけで済みます。

### 実測（ルートモンスター400体、魔力21〜130）

```
25HP x1   26HP x5   27HP x14  28HP x33  29HP x61  30HP x54
31HP x49  32HP x62  33HP x53  34HP x48  35HP x14  36HP x6
```

スターターは Moss 32（魔力86）、Aqua 30（魔力68）、Ignis 28（魔力46）です。**魔力の中央値は81なので、実際には31〜33が最も多く出ます。**

下限25が出たのは1体だけ、上限36は6体です。極端な個体でだけ上下限に当たります。

### 回復だけでは決着しません

回復しかしない個体を、攻撃してくる相手に200戦ぶつけた結果です。

```
魔力  20（回復25）  相手の勝ち 200/200   平均6.0ターン
魔力  70（回復30）  相手の勝ち 200/200   平均6.0ターン
魔力 130（回復36）  相手の勝ち 200/200   平均6.0ターン
魔力9999（回復36）  相手の勝ち 200/200   平均6.0ターン
```

**どの魔力でも1戦も引き延ばせません。** 連続使用不可があるため実質2ターンに1回で、ダメージが上回ります。ご懸念の「回復だけで決着しなくなる」は、上限より先に連続使用不可が防いでいます。上限36は保険として残してあります。

## 4. 直したバグ：MP回復が「HP満タン」と表示されます

**`amount=0` を「HP満タン」と表示する実装だと、マルチゲイズで誤表示が出ます。**

MP回復が `heal` イベント（`amount: 0`）として出ていました。HPは1も動いていないのに、です。マルチゲイズ（MP10回復）を撃つたびに回復演出と「HP満タン」が出ます。

**MP回復を専用イベントに分けました。**

```ts
{ type: 'mp', actorId, targetId, skillId?, amount }
```

`amount` はMP上限で切ったあとの実回復量です。該当する技はマルチゲイズだけです。

**UI対応**: 知らないイベント型を無視する作りなら、このままでも誤表示は消えます（MP回復が何も出なくなるだけです）。MPの演出を出す場合は `mp` を拾ってください。

## 5. テスト（7件追加、計276件）

- 魔力が高いほど多く回復すること、段ではなく連続して増えること
- 魔力70で技どおりの30になること
- 魔力0・1・500・9999でも上下限を越えないこと、上下限に届くこと
- 0〜200の魔力すべてで整数が返ること（UIが表示する値なので）
- 全30技に `getMoveHealing` を渡して、回復技だけが正の値を返すこと
- 戦闘中の回復量が術者の魔力どおりで、`getMoveHealing` と一致すること
- HP満タンで使ったとき `amount: 0` が返ること
- MP回復が `heal` として報告されないこと、`mp` として報告されること
- HPが半分以下の個体が回復を選ぶこと
- HP満タン・かすり傷では回復を選ばないこと
- 前のターンに使った回復技を選び直さないこと
- 回復技を持たない個体の挙動が変わっていないこと
- HP1から満タンまで全ての値で、回復一辺倒にならないこと

**既存のテストで担保済みのもの**（今回は重複させていません）

- 攻撃しないこと（ダメージイベントを一切出さないこと）
- 連続使用不可（2ターン目が `blocked` / `reason: 'consecutive'` になること）
- 残り5だけ回復したとき `amount: 5` が返ること

## 6. 敵AIが回復を使うようになりました（追加対応）

**当初の報告**: 技セットに回復技を入れても、敵AIは**1165ターン中0回**しか使わず、回復を持たせたまま43戦落としていました。`createBasicPolicy` が期待ダメージだけで技を選ぶため、期待ダメージ0の回復技は通常攻撃に永久に負けます。

**ユーザー判断で、使うようにしました。**

```ts
createBasicPolicy(rng, {
  healBelowHpRatio: 0.5,   // HPが半分以下になったら検討する
  minHealUseRatio: 0.7,    // 回復量の7割以上が無駄にならないときだけ使う
})
```

既定値です。`defendBelowHpRatio` と同じく、呼び出し側で差し替えられます。

**2つの条件を両方満たしたときだけ使います。**

1. HPが半分以下 — 余裕があるなら殴ったほうがよいため
2. 回復量の7割以上が実際に入る — 回復30をHP4の傷に使うのを防ぐため

守るより先に判定します（HPが減っているなら、身を固めるより治すほうが良いので）。連続使用不可の技は、前のターンに使っていればそもそも候補にしません（使っても `blocked` になって1ターン無駄になるため）。

### 測定（200戦、回復技を持たせたAqua対Ignis）

```
                        変更前        変更後
回復を選んだ回数        0 / 1165     233 / 1357ターン
回復を持っていて負け    43 / 200     18 / 200戦
```

**負けが43→18に減りました。**

### 無駄打ちと暴発の確認（300戦）

```
回復を選んだ回数                      356回
うち回復量の7割未満しか入らなかった     0回
実際に入った割合の最小値               100%
連続使用不可で拒否されたターン           0回
```

**1回も無駄打ちしていません。** 選んだ356回すべてで回復量が丸ごと入っています。

### アリーナは難しくなっていません

アリーナの各戦を200回ずつ測りました。

```
          #1    #2    #3    #4    #5   ボス
Moss   変更前  94%   79%   69%   54%   48%    1%
       変更後  94%   79%   69%   53%   48%    1%
Ignis  変更前  86%   72%   64%   47%   43%    0%
       変更後  86%   72%   64%   47%   42%    0%
Aqua   変更前  93%   90%   85%   72%   65%   30%
       変更後  93%   90%   85%   72%   65%   30%
```

**差は1ポイント以内です。** アリーナの敵の既定セットは威力順に埋まるので、サポート技の回復はほぼ入らないためです。回復を覚えた敵が出たときだけ効きます。

スターターの勝率差も42.0ポイントから動いていません。

**注記**: 上の表はスターターそのままでボスに挑んだ場合です。実際の周回では5戦分の報酬と融合を経ているので、ボスの1%・0%はこの測定の条件によるものです（変更前から同じ値なので、今回の変更とは無関係です）。
